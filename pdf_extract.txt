1 What you are building
Four puzzles that run in a browser, during a live event, while teams move around a campus. A cipher, an
8×8 colour grid, a wire-rotation circuit, and a 3D room you look around and pick things up in.
The thing worth understanding before you write anything is how little of this is new. The platform
already had a submission pipeline, a scoring ledger, sessions, and a hunt grader that compares hashed
answers and deducts hint costs. None of it was modified. Four puzzles with a 3D scene were added
without touching a line of the pipeline.
That is the test of whether a boundary is in the right place, and it is the single most useful thing to copy
from this build.

The assembled code
All four unlock at once. There is no chain: teams take whichever station is free, which is what stops four teams
queueing behind the slowest puzzle. Each is worth 100 points; hints cost 15 then 25.
W H Y N O C H A I N
A chain reads better on paper — solve this, unlock that. In a room with four teams and four stations it means three
teams standing still. The platform's gradeHunt supports chaining through nextSlug ; this event simply leaves it
unset.
1.2 The one thing that shipped broken
Before the design, the outcome — because it is the most useful thing in this document.
The build passed nine per-task code reviews. Every task was correct against its own brief. Then a whole-
branch review ran and found that no team could play at all: fifteen real teams in the live database had zero
progress rows between them, and every one of them would have opened the page to a spinner that never
resolved, with no error shown.
The cause was a seam. Progress rows were created in one place ( /api/enter ) and deleted in another
( scripts/seed-hunt.ts , which wipes them on every reseed). Nothing put them back. One task owned the
seed, another owned entry, and nobody owned the lifecycle between them.
W H AT TO TA K E F R O M T H I S
Reviewing each piece against its own specification cannot find a bug that lives in the gap between two pieces.
Something has to look at the whole thing, and it has to look at the running system rather than the source — the fault
was invisible in code review and obvious in one database query.
Part 10 catalogues this and the others. Read it before you build, not after.

T W O D E TA I L S W O RT H S T E A L I N G
The answer is never stored. Only hashAnswer(code) reaches the database. Anyone with database access still
cannot read the answers.
Hints are a cost, not a lockout. The award is Math.max(0, points - spent) — a team that buys every hint
still scores something and keeps playing, rather than being punished into standing still for forty minutes.
2.2 Cosmos is not MongoDB
The database speaks the MongoDB wire protocol and is not MongoDB. Two of its quirks bit this build directly.
WHAT YOU SEE
WHAT IT IS
Error 16500
Throttling, not failure. You exceeded provisioned RU/s. Retry it. This appeared while deleting 55 test
teams in one call — the helper below exists precisely for it, and the throwaway cleanup script that hit
the error had not used it.
A unique index
will not create
Only permitted on an empty collection. The coin system is keyed by _id for this reason — uniqueness
Cosmos will not give you as a constraint, obtained by making the unique thing the key.
src/lib/db/retry.ts
54 lines
1 /**
2 * Retry around Cosmos DB throughput throttling.
3 *
4 * Cosmos's RU-based Mongo API answers error 16500 when a request would exceed
5 * the account's provisioned throughput, with a `RetryAfterMs` hint in the
6 * message. It is NOT a failure — it means "ask again shortly". A real MongoDB
7 * server never does this, so nothing in the driver handles it: `retryWrites`
8 * has to be off against Cosmos anyway (see `client.ts`), so an unretried 16500
9 * surfaces to the caller as a hard error.
10 *
11 * That matters most at exactly the wrong moment. This platform's whole premise
12 * is 500 people acting inside the same five seconds, and a burst like that on a
13 * modest RU allocation is precisely when 16500 appears — so a submission that
14 * should have been accepted would come back as a 500 to a participant.
15 *
16 * Wrap bulk or burst-prone database work in this. It is not a substitute for
17 * provisioning enough throughput for the event; it's what stops a brief spike
18 * from becoming a lost submission.
19 */
20
21 const THROTTLE_CODE = 16500;
22
23 function retryAfterMs(err: unknown, attempt: number): number | null {
24

25

26
27
// Cosmos puts the hint in the message: "Error=16500, RetryAfterMs=8, ..."
28

29
const match = /RetryAfterMs=(\d+)/.exec(text);
30
const hinted = match ? Number(match[1]) : 0;
31
32
// Honour the hint but never hammer: back off geometrically as attempts climb.
33

3 The puzzle logic
All three of the flat puzzles keep their logic in framework-free modules under src/lib/hunt/ , unit-tested
with Vitest. The React components render state and forward clicks; they contain no rules.
This is not tidiness. The existing verification script needs a running server and a live database, which is
fine for integration and useless as a development loop. Pure modules can be tested in milliseconds, and
the circuit's connectivity bug took four rounds to kill precisely because it needed thousands of seeded
runs to reproduce.

3.3 The circuit, and four rounds of being wrong
A grid of wire tiles; clicking rotates one 90°. The board is scrambled at seed time, and the scramble must never
produce a board that is already solved — that would hand out free points with nothing erroring to say so.
That guarantee took four attempts. The full account is in part 10; the working version is here.

13 * "no puzzle starts solved" looks identical whether it's really broken or

18 * team below claims whatever the database says is still unclaimed (see
19 * `freshCoin()`), so every run gets brand-new teams with brand-new,
20 * never-touched progress rows — a second run without reseeding will mostly
21 * still pass, because there's no stale team left around to collide with.
22 * Reseed before every run anyway: this script's expected numbers (85, 60, 100
23 * points; hint costs of 15 and 25) are only true of whatever `seed-hunt.ts`
24 * most recently wrote. If that file is edited — a hint cost changed, or (see
25 * the deliberate leak-proof this script was built to catch) a reveal code
26 * temporarily added to a challenge's config — the live challenge documents
27 * only reflect that edit once seed-hunt.ts has actually been re-run. Skip the
28 * reseed and this script checks the OLD config, silently.
29 *

31 * one-way transition — nothing in the app ever unclaims one — and a coin is a
32 * physical printed disc: one left claimed by a test run is one a real team's
33 * disc silently fails to enter with at the door. So this script tracks every
34 * team it creates under five fixed, reserved names (EPHEMERAL_TEAM_NAMES) and
35 * releases them — coin, team, participant, progress, score events — in a
36 * `finally` around the whole run, whether it finishes or throws. And because
37 * those names are reserved for this script alone, `releaseEphemeralTeams()`
38 * ALSO runs once at the very start, so a run that got killed before its own
39 * `finally` could fire (a hard process kill bypasses `finally` entirely) is

9.2 Checks that can actually fail
Two of these deserve attention, because the obvious version of each proves nothing.
The clamp. With 100 points and hints costing 15 and 25, the award can never go negative — so asserting "it
clamps at zero" against a real puzzle passes while testing nothing. It runs against a synthetic challenge whose
hints cost more than it is worth.
The leak. It strips non-alphanumerics from the response before searching. The earlier version substring-
matched the whole code and reported green while the Mystery Room shipped its answer as
["AR","CH","IV","ES","88"] — five fragments that join into the code. A guard written for exactly one bug
missed it on a technicality.
P R O V E A N E W C H E C K C A N FA I L
Deliberately break the thing it watches, watch it go red, then fix it. Three separate checks in this project passed for
the wrong reason and were caught only by someone doing this.
9.3 Leave the database as you found it
The script claims coins from a finite pool of sixty printed discs shared with the real event. Early versions never
released them: after roughly ten runs, 56 of 60 coins were held by test teams, and any of those discs handed to
a real team at the door would have been silently refused.
It now tracks everything it creates and releases it in a top-level try/finally , with deterministic identifiers
and a sweep before it starts — so a run killed mid-flight is cleaned up by the next.
T E S T DATA O N A R E A L L E A D E R B OA R D
Those teams also carried score events. A materialised hunt leaderboard showed 32 rows of test teams, top-ranked,
with the real teams below all of them. That is the failure everyone in the room sees at once.
10 What went wrong
The most useful part of this document. Every one of these passed a code review before it was caught, and
most were caught by measuring rather than reading.
10.1 Nobody could play
Severity: total. Fifteen real teams, zero progress rows, a spinner that never resolved and no error shown.
Rows were created in /api/enter and deleted by seed-hunt.ts . Nothing backfilled them. One task owned
the seed, another owned entry, and no task owned the lifecycle. Nine per-task reviews passed because each
piece was correct in isolation.
Found by: a whole-branch review that queried the live database instead of reading the diff.
Fixed by: upserting the rows on every progress read, so any page load heals the gap.
10.2 Four leaks of the same shape

10.4 Hints that cost 40 points to mislead you
Both Mystery Room hints were factually false.
"Two are behind you when you start" — all five props are in front, and the camera's yaw is clamped to ±0.85
rad, so behind you is unreachable by construction. A team following that hint could not perform the action it
described.
"The fragments read in the order the objects are numbered" — describes a manual assembly step that does not
exist; the component assembles the code and fills the box.
The grid's equations were worse: they asked for "Peter's floor number", which is defined nowhere in the app,
the config, or the hints. A team buying both hints still could not solve it, and the unpunished fallback was to
click all eight swatches and guess.
CO N T E N T I S N OT D E CO R AT I O N
These cost 15 and 25 points each. Wrong content is a scoring bug that no test catches, because every test asserts the
mechanism rather than the meaning. Someone has to read the hints as a player would.
10.5 Smaller ones, and what they share
Hints were free. gradeHunt deducted hint costs from day one; nothing ever incremented hintsUsed .
The deduction had never executed.
Failures read as wrong answers. submit() ignored res.ok , so a 401 or 500 rendered as "Not that
one."
The manifest did nothing. The prop component never read slot.model , so pointing it at a GLB silently
kept the placeholder.
The verifier consumed the event's coins. Five per run, never released, from a pool of sixty physical
discs.
CI never ran the tests. Forty unit tests including a 200,000-seed sweep, executed only when a human
remembered.
W H AT T H E Y H AV E I N CO M M O N
Not one of these throws. Every single one leaves the application working perfectly and the event subtly unfair or
unrecoverable. That is the class of bug this kind of event generates, and it is why the verification script is the
highest-value file in the project.
11 Running it
What the coordinator does, in order.
11.1 Before the doors open
1. Scale Cosmos RU up. The default throttles under load — deleting 55 documents in one call was enough
to trigger error 16500. Thirty teams submitting at once will find it faster. Scale back down afterwards; it is
billed hourly.
2. Reseed, then run the verifier. Both, in that order. A green run against the real deployment is the only
evidence the thing in front of you works.
3. Check the coin pool. Every disc handed out must be unclaimed. A coin consumed by a test run is silently
refused at the door, and the team has no idea why.
4. Read the hints aloud. As a player, not as the person who wrote them. That is how the false ones were
caught.
11.2 When something breaks mid-event
Points are an append-only ledger, so almost any scoring mistake is recoverable without editing a total by
hand.
